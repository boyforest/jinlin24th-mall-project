# 二十四养双业务 · 实施交接

日期：2026-10-24。依据：当前 `main` 的 `cf295c1` 及已认可的第二版交互设计。本目录只包含实施方案，没有实现业务代码。

## 本轮边界

用户已确认：**咖啡首版支持浏览和加购；微信支付商户及收款配置就绪后，再开放线上下单。** “线下结算”仅指原有推荐官佣金结算，不等于咖啡到店付款。

| 本轮实施（阶段 A） | 后续实施（阶段 B） | 暂不纳入 |
| --- | --- | --- |
| 首页双入口、商品选购独立页面、咖啡菜单和规格 | 咖啡真实下单、支付、退款 | 美团／抖音券 SDK |
| 独立咖啡购物车、商品／咖啡切换、玻璃浮栏 | 接单／制作／取餐工作台、叫号屏 | 咖啡分销和佣金 |
| 统一订单列表与业务分类，保留已有商品订单能力 | 两家店各自商户收款的全链路 | 多门店平台、原料库存、多仓改造 |
| 当前管理后台内维护咖啡门店、分类、饮品、规格 | 咖啡店员账号与门店权限隔离 | 广告推送业务重做 |

阶段 A 的咖啡购物栏保留已选内容与金额，按钮显示“暂未开放”，不创建待支付订单、不调用商品支付、不假装点单成功。开发预览可展示未来完整状态，但正式包不能携带演示订单或演示接口降级。

## 两个对话怎么分工

- **前端对话**：先读 [前端实施方案](frontend-plan.md)，再读 [共用接口与边界](api-contract.md)。负责 `c-uniapp/` 和 `admin-web/`，不修改 Java、SQL、支付配置。
- **后端对话**：先读 [后端实施方案](backend-plan.md)，再读 [共用接口与边界](api-contract.md)。负责 Java、SQL、配置示例和接口测试，不修改两端前端源码。
- 共用接口以 [api-contract.md](api-contract.md) 为唯一基准。变更由后端对话先更新该文件，前端对话同步适配；不要各自改一份类型或接口名称。
- 本目录不代表相关接口已经存在。标明“新增”的接口和文件均是待实施内容。

建议前端功能分支 `uniapp-dual-business-ui`，后端功能分支 `uniapp-coffee-backend`，沿用现有 `uniapp-…` 命名，不加 `codex/`。本套文档位于 `uniapp-dual-business-plan` 分支。

**并行开发必须使用两个独立 Git worktree／检出目录。** 同一个目录里开两个对话后分别切分支，会互相切走分支；文件范围分开也不能解决这个问题。两个工作目录都应从包含本套文档的同一提交开始。若文档尚未提交，先只提交本目录，再创建两个工作目录，不能顺带提交已有无关改动。

## 已核对的关键事实

1. 当前技术栈是 Spring Boot 3.2.5／Java 17、uni-app／Vue 3／Pinia、React／Ant Design，不需要套换其他项目底座。
2. 商品下单已占用 `inventory` 库存；取消按原仓还库；支付回调推进商品订单到“待发货”并关联分销。部分旧注释与实现不同，以实际执行代码为准。
3. `OrderServiceImpl.userPage()` 当前不返回 `items`。统一订单卡片需要新增批量摘要查询，不能指望现有列表已有缩略图、规格。
4. 微信支付目前使用一套 `WxPayConfig`；不能把咖啡商户号覆盖到现有全局配置。
5. `AdminJwtInterceptor` 验证管理员身份，但不能据此认定已经具备门店数据隔离。阶段 A 仅开放给可信的平台管理员；店员／叫号屏账号列入阶段 B。
6. 原生 TabBar 在业务子页不会自动展示，必须明确补齐导航方案，不能照抄 HTML 的模拟导航栏。

视觉参考：预览中的无框节气首页、并列无框入口、文字业务页签、暖白商品卡片、玻璃浮动购物栏。当前预览保存在本机 Codex 产物目录，具体路径见前端方案。手机壳、状态预览工具、演示数据均不是正式产品内容。
