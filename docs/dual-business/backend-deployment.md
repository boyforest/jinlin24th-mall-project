# 咖啡后端阶段 A · 实施与部署

本轮分支：`uniapp-coffee-backend`，基线 `d96f255`，与前端文档基线一致。实现范围是咖啡公开目录、独立购物车、平台管理员菜单维护及统一订单摘要查询。共用契约继续以 `api-contract.md` 为准，未改路径、业务码或字段约定。本文记录实际实现与验证，不代表已部署到业务环境。

## 代码与行为

- 五张咖啡表独立于原商品购物车、仓储、分销及支付。没有咖啡订单、支付或退款入口。
- 仅精确匹配的 `GET /user/coffee/store`、`GET /user/coffee/menu` 放行用户鉴权。其他用户操作沿用用户 token；管理接口沿用管理员 token，并在服务端每次检查启用的 `SUPER_ADMIN` 角色。
- 首版唯一主门店由 `primary_slot=1` 的唯一键及 CHECK 约束保证，不约定门店 ID 为 1。没有真实门店或目录未启用时，公开接口返回 `90401 / HTTP 404`。
- `COFFEE_CATALOG_ENABLED` 默认 false。启用只允许浏览和独立加购；`placeOrder`、`payOnline` 在代码中始终为 false。门店 CLOSED/PAUSED 时仍可浏览加购，原因文案与线上点单能力分开。
- 管理端完整返回下架/停用数据。饮品与全部规格在一个事务中保存；保留已有 SKU ID，遗漏的旧 SKU 停用，恢复已有组合时复用旧 ID。冲突组合、跨饮品 SKU、跨店分类和仍有在售饮品的分类停用会被拒绝。
- 加购及菜单维护先获取门店行锁，使用 READ COMMITTED 事务在锁后读取最新数据；单店小规模下以此串行化目录与购物车写入。购物车唯一键保证每用户/门店/SKU 一行；已有行数量累加，超出 99 整体拒绝。PUT 仍用用户 ID 和版本做数据库条件更新；单行有效更新及全选实际变更都会递增版本。
- 行锁读取禁用查询缓存并清理当前会话的旧读取。公开目录、购物车列表及统一订单查询采用一致性读取；购物车展示批量关联当前价格和可售性，停用后仍允许本人读取、取消勾选、减量和移除。
- POST 加购是增量操作，超时后先读取确认，不能自动重试。全选只更新本人当前门店可售行，不重置不可售行已有选择。
- 新 DTO 拒绝客户端身份、改价、支付开关等未知字段；JSON 数量、版本和金额拒绝小数、字符串或布尔强转，价格和版本限制在 JS 安全整数内；请求体 ID 必须是十进制字符串。
- 统一订单只读取当前用户真实商品订单，按创建时间和 ID 降序分页，每单最多三个快照摘要并汇总全部明细数量。四次批量 SQL 分别读取计数、订单页、明细和支付依据，不逐单取详情。咖啡条件返回合法空页。
- 旧商品金额以 BigDecimal 精确换算为分。未支付时 `paidAmountCent=null`；成功支付流水优先，历史订单可由 `payTime` 佐证，退款后仍表示原支付金额。返回 ISO 8601 的 `+08:00` 时间，不返回地址、买家或推荐官手机号。

单店行锁是本轮明确的小规模实现方式；将来需要并行处理大量门店/购物车写入时，再细化锁范围。原商品交易服务、支付回调、退款、超时还库、分销和前端源码均未修改。

## 存量升级

1. 备份业务数据库。以有建表权限的迁移账号，先在测试环境执行 `sql/migrations/20261024_coffee_catalog_cart.sql`，核验五张表、唯一键、外键、CHECK 约束。运行环境为 MySQL 8.0.16+；现有商品表结构和数据不变。
2. 在生产执行同一增量脚本，**不要重新执行 `sql/jinlin24th_init.sql`**。业务账号保留现有最小 DML 权限；不要为应用增加 DDL 权限。
3. 部署兼容的后端，先保持 `COFFEE_CATALOG_ENABLED=false`。用可信 SUPER_ADMIN 查询管理上下文，建立真实门店、分类、饮品和允许的 SKU 组合。已有门店时不允许创建第二家。
4. 设置 `COFFEE_CATALOG_ENABLED=true`，按现有部署方式重启/重建后端容器。`docker-compose.yml` 已转发该环境变量。商品商城展示名通过 `GOODS_STORE_NAME` 配置，默认金霖二十四养。
5. 完成下面的接口验收后，再发布依赖新接口的前端。

示例迁移命令（使用部署环境已有的登录配置，不把密码写进命令或仓库）：

```bash
mysql --login-path=jinlin-migration jinlin24th < sql/migrations/20261024_coffee_catalog_cart.sql
```

重复执行行为：`CREATE TABLE IF NOT EXISTS` 跳过已存在表，不清空记录，也不会自动修复已有同名表的结构漂移。MySQL DDL 隐式提交，不能声称整份脚本可事务回滚；部分执行后应逐表检查，再补齐未完成部分。

## 新安装与本地联调

新安装使用现有 `deploy/mysql/init/01-schema.sql` 的 SOURCE 入口，加载同一份 `sql/jinlin24th_init.sql`。新安装结构已包含咖啡五表，没有默认咖啡门店、饮品、交易或商户配置。

`sql/coffee_demo_seed.sql` 只供本地/测试显式执行，不被部署初始化脚本引用；重复执行不会重复造演示菜单，已有真实门店时不写入演示数据。生产不能执行它。前端联调以 API 返回的实际 ID 为准。

本地配置参考 `application-dev.example.yml`；生产参考 `application-prod.example.yml` 和 `.env.example`。不复制生产密钥到本地，也无需咖啡商户凭证。

## 验收与已执行验证

- 匿名访问两个公开 GET 成功；购物车、统一订单和管理接口需要对应登录；非 SUPER_ADMIN 直调新管理服务返回 403。
- 闭店依然允许浏览/加购；目录关闭或门店缺失返回明确错误；购物车旧条目在目录关闭时仍可移除。
- 两账号购物车完全隔离；同 SKU 24 路并发加购只产生一行、数量 24；90 件起点并发追加时仅允许九次成功；同一版本并发修改只有一次成功；并发建立首店只成功一次。
- 保存/恢复/停用规格、价格和下架变化、事务失败回滚、JSON 参数类型和上界、版本冲突、全选路由及版本语义均有测试。
- 统一订单覆盖状态组、单状态和不兼容筛选、分页总数与顺序、快照、三条摘要与总件数、分制金额、未支付/退款支付依据、字符串大 ID、时区及实际 SQL 次数。

验证命令：

```bash
mvn test
scripts/test-coffee-mysql.sh
mvn -DskipTests clean package
```

`mvn test` 中原有 `ApplicationConfigSecurityTest` 依赖被 gitignore 的本地 `application-dev.yml`；本轮在独立工作目录按示例生成本地配置，并补本地 SQL 日志及 Swagger 开关后运行。新测试不加载应用数据源配置：默认使用 H2；MySQL 验证只接受 `127.0.0.1` 上名为 `coffee_phase_a_test` 的一次性测试库。打包前移除本地测试 profile，避免将其带入交付包。

`scripts/test-coffee-mysql.sh` 创建专用 MySQL 8 容器，校验含历史订单的存量升级、重复迁移、部署入口的新安装、演示数据的显式重复执行，再运行真实事务/数据库和 MockMvc 接口测试；退出自动删除专用容器及卷。它不读取业务库或生产连接配置。

2026-10-25 实测结果：全量 `mvn test` 230 项通过，失败/错误/跳过均为 0（其中本轮新增 32 项）。30 项咖啡数据库及 HTTP 行为测试也在一次性 MySQL 8 中通过；另两项验证应用与 Compose 配置节点。存量迁移、重复执行、新安装及显式演示数据验证通过。`mvn -DskipTests clean package` 通过，已检查交付 JAR 不包含本地测试 `application-dev.yml`。

本地验证不能替代真实前后端联调、部署环境迁移演练和微信真机验收；本轮未连接生产数据库或发布服务。

## 回退

先将 `COFFEE_CATALOG_ENABLED=false` 并重建后端，关闭公开目录及加购；本人已有购物车仍可查看与移除。需要回退版本时，同步回退依赖新接口的前端或关闭其入口，再回退应用。保留五张表和购物车数据，不以删表作为第一步。原商品业务继续使用原链路与原支付配置。

阶段 B 必须另补交易契约、独立商户和门店权限后再实施；本轮没有可通过配置开启的咖啡下单/支付能力。
