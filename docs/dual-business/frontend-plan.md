# 前端实施方案 · 阶段 A

日期：2026-10-24。范围：小程序 `c-uniapp/`、管理后台 `admin-web/`。这是修改方法和文件清单，不是已完成的代码实现。共用字段和接口以 [api-contract.md](api-contract.md) 为准；项目与分工见 [README](README.md)。

## 1. 交付目标与限制

在现有项目上落地已认可的第二版风格，交付：首页、独立商品选购、咖啡菜单与规格、两种独立购物车、统一订单列表，以及同一管理后台中的咖啡菜单维护。

**咖啡本轮只能浏览和加购。** 收款配置就绪前，不能创建咖啡订单、调用现有商品支付、自动转成到店付款，或展示假的支付成功、制作进度和取餐号。商品已有的下单、微信支付、收货和推荐官展示继续保留。

不修改 Java、SQL、后端支付配置、部署密钥；不引入新前端框架，不用外部点单项目替换现有底座。未来支付／店员工作台／叫号屏不计入本轮完成条件。

## 3. 页面与导航改法

### 3.1 首页与商品选购

将 `pages/home/index.vue` 中“节气品牌展示”与“商品搜索／列表／购物篮”拆开：

- 首页保留 `SolarTermHero`，添加两个等权业务入口；商品入口到 `pages/goods/index`，咖啡入口到 `pages/coffee/index`。
- 把现有商品搜索、分类、分页、详情跳转、加购、购物篮抽屉迁入商品选购页。优先搬移现有逻辑，不重写已通过验证的商品接口和购物车状态。
- 原有广告公告、运营 Banner 和弹窗的配置语义不能因视觉稿省略而删除。首页入口下方可继续安排运营内容，原商品检索也必须保留；本轮不扩展推送业务。
- 保留节气自动计算、真实墨字资源、季节定位、日期与倒计时。预览中的固定日期不是生产数据。
- 商品售价和合计仍以服务端 `effectivePrice` 为准，不能改为按前端会员判断计算价格。

### 3.2 四项导航

保留首页／购物车／订单／我的原生 TabBar。商品与咖啡使用独立非 Tab 子页，返回键由页面栈处理。

设计稿中的业务子页也有四项导航：建议新增共享 `BusinessTabBar.vue`，仅在商品／咖啡子页呈现，与现有 TabBar 图标、颜色、字号和占位保持一致，点击时调用 `uni.switchTab`。原生 Tab 页不要重复渲染该组件。不要为此重写整个应用导航。

`switchTab` 不能携带业务查询参数：进入购物车前，先把当前业务写入共享上下文，再切换 Tab。原生导航栏和微信胶囊继续交给微信；必要时以真机为准微调模拟底栏的一致性。

### 3.3 咖啡菜单与规格

- 先加载门店能力，再加载菜单；浏览使用公开接口，不因初始化购物车或过期登录态强制跳登录。
- 门店卡片展示真实名称、地址／营业时间；“营业中”只表示门店营业，不等于已开放线上下单。
- 本轮固定显示点单筹备说明；购物栏按钮按服务端能力禁用，文案“暂未开放”，不提供可点击的提交入口。
- 温度和甜度来自后端可售 SKU 的有效组合；不能自行拼出不存在的“冰／无糖”组合。价格随选中 SKU 更新。
- 规格切换只更新弹层内选中状态，不销毁并重新播放整个弹层；加入后给出购物篮数量和金额反馈。
- 游客可以浏览和选择规格，点击加购时引导登录；返回保留分类、滚动位置、饮品及所选规格，不自动重复提交上次加购。
- 暂停营业、停售、菜单为空、加载失败均需明确呈现，不能以示例饮品替代真实失败状态。

### 3.4 两种购物车

现有商品 `useCartStore` 保留；新增独立 `useCoffeeCartStore`，页面和浮动购物篮共用它。不能把咖啡数据写进商品 `/user/cart`，也不能把咖啡数量加入商品结算快照。

- 顶部页签显示各业务购物车总数量；底栏“已选”和金额只统计当前业务的可售勾选条目。
- 勾选、增减、移出、全选、规格文案使用共享呈现组件；数据请求通过适配层分别进入商品／咖啡 store。
- 两种业务独立保存选择、错误和请求锁；当前业务更新中显示反馈，防止连续提交。失败后重新读取实际状态，不能把失败更新当作成功。
- 咖啡数量更新带 `expectedVersion`；冲突时重新加载并提示。不要自动重放不确定是否成功的 POST 加购。
- 账号退出、过期或切换时清理账号相关缓存，异步响应落地前再次校验账号；不能把上一账号的购物车显示给新账号。
- 不可售项保留原因与移出入口，不计入可结算金额。空、加载失败、更新失败与“未登录”分别处理。
- 商品结算仍调用现有服务端预览并保留推荐官信息；咖啡结算在本轮始终受能力限制，不能借用商品确认页的收货字段。

### 3.5 统一订单

接入新增统一列表查询，不在前端分别取两页后拼接。业务页签为全部／商品订单／点单订单；业务切换后重置为该业务的“全部”，请求序号防止旧响应覆盖新筛选。

列表使用 `businessType + ':' + id` 作唯一 key。展示服务端返回的商品摘要，不逐单请求详情补图。商品订单详情继续进入原页面；阶段 A 咖啡订单分类应是正常空状态，不显示演示记录或假的取餐号。

状态映射集中维护。未付款显示“应付”，仅有真实支付依据时显示“实付”，不能因为 `payAmount` 非零就显示已付款。商品原来的待付款、待发货、待收货、完成、取消、退款能力不得丢失；未来咖啡状态另有“待接单／制作中／待取餐”。

预览只演示有限订单状态，不能把它的筛选数组直接当业务规格：正式页补齐共用契约中的“已关闭／已取消”和售后分组；全部业务使用状态组，单业务按标准状态筛选。后续咖啡接入时须补“待接单”，不能把付款后统一画成制作中。

### 3.6 管理后台

在现有后台增加“咖啡菜单”入口与页面，沿用现有 Ant Design 风格，不把小程序玻璃界面搬进管理端。

页面先请求管理上下文；无门店时允许授权管理员建立首个门店，已有门店后不显示新增门店入口。仅可信平台管理员能维护门店资料、分类、饮品、规格价格及停售状态。使用现有图片上传。前端菜单隐藏只是体验处理，后端必须做真实权限检查。

本轮只做菜单维护，不做咖啡订单工作台、叫号屏、店员账号管理和商户号编辑。不能用一个“开放点单”开关绕过收款就绪检查。

## 6. 分步实施与联调

1. **基线**：确认工作目录、分支、仓库指引和已有未提交内容；记录现有小程序构建结果，不改无关文件。
2. **共享外观**：先做共用变量、页签、玻璃浮栏，保留不支持背景模糊时的暖绿实底回退。微信真机效果优先于桌面 CSS 效果。
3. **页面拆分**：迁出商品选购，再完成无框首页；检查登录返回、原广告／搜索／商品详情是否仍可达。
4. **咖啡菜单与购物车**：按契约接公开菜单、有效 SKU、登录加购和独立状态；默认禁止咖啡下单。
5. **统一订单**：接后端新查询；未上线前仅开发环境模拟，不能在生产用前端拼页替代。
6. **后台维护**：补咖啡菜单页面，接后端真实管理上下文和维护接口。
7. **联调与截图**：使用真实服务验证持久化和错误状态；截图至少包含首页、两种购物车、规格弹层、订单分类和首发禁用状态。

前端可以先做页面与契约模拟；后端应先交付公开菜单和购物车，再交付统一订单摘要及管理维护。两端不要同时修改共用契约或对方目录。

## 7. 验收标准

- 首页没有节气卡片边框，两入口不再是独立白色卡片；小屏能识别且可访问两个入口。
- 购物车／订单业务页签、商品／咖啡卡片、价格、浮栏在全局一致，未出现另一套配色或字体。
- 玻璃底栏不挡最后一条可操作内容，人民币符号不换行，安全区不重复计算；关闭模糊后仍清晰。
- 游客刷新首页／菜单不跳登录；加购登录返回后保留原位置和规格，未重复加购。
- 两购物车勾选、数量、金额、错误相互独立；商品结算不含咖啡；账号切换不串数据。
- 服务端拒绝的 SKU、停售项、价格变化和版本冲突均有反馈，失败不当成空内容。
- 收款未就绪时，菜单浮栏、购物车页及购物篮弹层都不能触发咖啡下单／支付。
- 统一订单正确分页和筛选；阶段 A 咖啡分类为空；商品原有交易操作继续可用。
- 后台能维护真实咖啡数据，未授权用户不能靠直接 URL 进入维护操作；后端仍独立校验权限。

前端完成后在各自目录运行 `npm run type-check`（小程序）、`npm run build:h5`、`npm run build:mp-weixin`、现有 `npm run test:solar-terms` 与 `npm run test:shopping-ux`；管理端运行 `npm run build` 和 `npm test`。新增行为测试覆盖业务隔离与能力限制，不为每条 CSS 写镜像测试。现有测试若依赖旧首页结构，应保留其行为断言并更新路径。

最后在微信开发者工具与 iOS／Android 真机检查布局、玻璃回退、返回行为和安全区。HTML 预览通过不等于小程序端通过。本方案不声称上述正式项目构建已执行完成。
