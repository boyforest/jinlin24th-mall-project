# 管理端分权、咖啡工作台与首页运营方案 · 讨论稿 V4

日期：2026-10-25。面向产品讨论，不是已确认的开发契约，也不代表功能已经实现。

已确认：首店位于医院、老年顾客较多，必须保留人工接单并规划接单接口；整单制作取餐，首版整单全额退款；超管需要账号与权限管理页。V4 合并此前讨论的首页广告与推荐养护最小改造，推荐内容可自行增加，前台最多展示六个产品。

本稿讨论管理端分权、咖啡店员工作台，以及小程序现有首页的广告与推荐养护展示。首页部分仅覆盖此前已讨论的运营区域，不扩大到其他小程序页面改版；AI 助手、团购券核销不进入本稿的首版开发范围。

## 1. 产品目标与现有基础

让商品运营和咖啡运营在同一套系统中各自工作。咖啡店员登录后，能迅速看清做什么、做到哪一步、交给谁；商品运营继续使用现有后台。

当前已有管理员登录、角色权限关联表，以及咖啡门店、菜单、规格维护能力。现有后台大部分接口尚未按业务权限完整拦截，咖啡维护目前只向超级管理员开放。

现有管理端路由尚无完整的账号与权限管理页；现有管理员认证控制器提供登录、自助改密、退出和账号选项查询，不等于已经具备管理员账号维护功能。下文账号管理页面与配套管理接口均为待实施内容。

用户已确认咖啡收款配置就绪，本轮可以规划真实下单与制作流程。正式开放仍须验证咖啡商户收款、支付回调、退款及对账链路；“已具备配置”不等于这些链路已验收。

首页已有“顺时养护”、活动横幅、公告及弹窗展示代码。现有 `marketing_activity` 表和管理表单支持图片、标题、副标题、位置、跳转、启停用、排序与起止时间；公开查询接口已按位置、状态和有效期返回内容。推荐养护的网格展示与后台位置选项是本轮待新增部分。

## 2. 账号与权限

同一个登录入口，按服务端返回的角色进入对应界面。

| 角色 | 默认界面 | 业务范围 |
| --- | --- | --- |
| 超级管理员 `SUPER_ADMIN` | 综合后台，可切换咖啡工作台 | 全部业务、账号分配、角色管理、平台配置 |
| 商品管理员 `GOODS_ADMIN`（拟定） | 现有商品后台 | 商品、商品订单、库存、仓储、客户、推荐官、优惠券及商品运营等非咖啡业务 |
| 咖啡管理员 `COFFEE_ADMIN`（拟定） | 咖啡制作工作台 | 授权咖啡门店的菜单、订单、人工接单/拒单、制作、取餐、流水与退款处理 |

首版咖啡管理员兼任店长与店员。一个咖啡角色可以分配给多个独立工作账号，不要求大家共用一个账号；制作和退款记录保留实际操作者。首版不再拆店长、制作员和收银员角色。

商品管理员的“全部非咖啡业务”不包括给自己提权、创建超级管理员、查看支付密钥或修改平台安全配置。共享首页广告与推荐养护的编辑发布权限见第 8 节，业务管理员是否开放仍待确认。

分权需要覆盖菜单、页面、按钮、接口、统计、详情和导出。咖啡账号不能直接请求商品接口；商品账号不能改咖啡订单。共享客户资料只向各业务返回完成当前服务所需的信息，不向咖啡账号开放全量客户名单。

角色变更或账号停用后，已有会话也要受到约束。首版新建的两个业务角色默认互斥；超管通过工作界面切换管理两边，不额外设计复杂的多角色选择流程。

### 2.1 超管专属「账号与权限」页（新增）

入口建议放在现有综合后台的「系统管理 → 账号与权限」，仅超级管理员可见并可访问。商品管理员和咖啡管理员都不能管理其他账号，也不能通过直接调用接口获得该能力。

首版用一个账号列表加创建/编辑表单完成主要操作，不单独建设复杂的权限配置平台。

账号列表展示登录账号、显示名称、角色、授权咖啡门店（适用时）、启用状态、最近登录时间。支持按账号/名称搜索，按角色和状态筛选。

| 操作 | 超管能完成的工作 |
| --- | --- |
| 新建账号 | 填写唯一登录账号、显示名称、临时密码，选择角色，咖啡角色选择授权门店 |
| 编辑账号 | 修改显示名称等基本资料；首版创建后不改登录账号 |
| 分配角色 | 在超管、商品管理员、咖啡管理员中分配角色，表单同时解释该角色能操作哪些业务 |
| 绑定咖啡门店 | 咖啡账号只管理明确授权的门店；当前首店从实际已创建门店中选择，不固定假设门店 ID |
| 停用/启用 | 离职或停用时禁止登录并让原会话失效；重新启用后可重新登录 |
| 重置密码 | 由超管设置新临时密码，使旧登录会话失效，下次登录要求修改临时密码 |

首版以停用保留历史操作人，不提供物理删除账号。新建账号和重置密码复用已有首次改密能力；页面不返回密码哈希，也不能查看原密码。

自己的密码继续通过现有自助改密流程处理。调整角色、授权门店后，服务端立即按新范围检查，界面重新获取权限；不依赖旧的浏览器缓存维持权限。

### 2.2 授权界面的范围与规则

首版按固定角色授权，选中角色后展示业务权限说明，不要求超管逐个勾选所有接口权限。角色对应的业务权限由实施方案统一维护；不纳入自定义角色、权限继承和任意权限组合编辑器。

超管能分配其他超管账号，但不能停用或降级最后一个启用的超级管理员。新建、停用、改角色、改门店授权和重置密码均记录操作人、时间与目标账号，不记录明文密码。

已有角色和账号需要在实施时明确兼容与迁移方式，不能重新执行初始化脚本来覆盖已有授权。账号管理只维护后台账号，不创建或修改小程序用户身份。

管理员账号列表、创建、资料修改、角色/门店授权、启停用和密码重置均需新增相应管理接口；所有这些接口的授权范围是超级管理员，不能只靠页面入口隐藏。

## 3. 咖啡界面的信息架构

共用现有系统和登录，新增咖啡界面布局，首版只有三个主要入口：

| 入口 | 使用目的 | 主要内容 |
| --- | --- | --- |
| 制作工作台（默认） | 接收并完成当天订单 | 待接单、待制作、制作中、待取餐，新单提醒 |
| 菜单管理 | 调整可售内容 | 售罄、恢复供应、上下架、饮品与规格维护、门店公告 |
| 订单与流水 | 查单、处理异常、核对收款 | 订单搜索、详情、退款、当日及日期范围统计 |

页面顶部常驻门店名称、营业/接单状态、连接状态和当前账号。超管额外显示切换商品后台的入口。首版以电脑和平板操作为主，手机提供窄屏排版，不另外开发一个店员小程序。

## 4. 制作工作台

### 4.1 排列与优先级

宽屏并列展示四列：待接单、待制作、制作中、待取餐。待接单放在最左侧，突出数量与等待时长。平板和手机改成带数量的页签，避免强行塞入四列导致规格文字太小；有待接单时提供明显提示。

每列按进入该阶段的时间从早到晚排列。跨日未完成订单仍保留，并标注日期，不能因为切换到新一天就消失。等待较久的订单用时间和轻量标识提示，不自动承诺预计取餐时间。

每张卡片展示：

1. 取餐号，例如 A018；订单完整编号放在详情。
2. 每种饮品的名称、数量、温度、糖度等规格；同单多杯必须能逐项读清。
3. 合计杯数与等待时长。
4. 有备注时独立突出显示。
5. 当前阶段的主要操作按钮。

所有制作所需规格直接显示，不强制点开详情。卡片点击可展开订单详情和操作记录。

### 4.2 操作规则

| 当前阶段 | 主要按钮 | 成功后的结果 |
| --- | --- | --- |
| 待接单（已支付） | 确认接单 | 移入待制作，记录接单人和时间 |
| 待制作 | 开始制作 | 移入制作中，记录操作者和时间 |
| 制作中 | 制作完成 | 移入待取餐，产生取餐通知任务 |
| 待取餐 | 确认取走 | 显示取餐号和杯数供核对，确认后完成履约 |

支付成功进入待接单，必须由店员确认后才能进入待制作。未支付订单只在订单查询中展示，不进入接单和制作队列。确认接单与开始制作是两个动作，首版不合并按钮。

待接单卡片完整显示饮品、数量、规格和备注，方便店员在制作前确认能否供应。接单本身不自动修改订单规格或金额。

待接单另设次级“无法接单”入口：选择缺货、暂停营业或其他原因，核对取餐号和整单金额后确认拒单，触发整单全额退款流程。管理端保存原因并显示真实退款状态；微信确认退款成功后才显示已退款。拒单订单不进入制作队列，退款失败仍需在异常订单中可见并继续处理。

接单与拒单必须有服务端接口支持，不能仅依赖前端按钮改状态。以下是拟定接口职责，具体路径在实施契约阶段统一：

| 拟定接口 | 职责 |
| --- | --- |
| `POST /admin/coffee/orders/{id}/accept` | 仅允许有本门店权限的咖啡管理员或超管，将已支付且待接单的订单确认为待制作 |
| `POST /admin/coffee/orders/{id}/reject` | 仅处理已支付且待接单的订单，要求原因，登记拒单并可靠发起全额退款；失败可追踪 |

重复接单、重复拒单和两台设备同时操作不能产生两次有效结果；接单与拒单相互排斥。无权限、状态已变更或退款正在处理时，界面说明实际情况并刷新，不允许跳过待接单直接开始制作。

首版按整单流转：一单多杯全部完成后才点击制作完成；暂不支持逐杯制作、分批取走和拆单。

开始制作、制作完成可直接操作，并展示处理中状态；确认取走增加一次简短核对，减少误交付。操作失败时卡片保留在原位置并说明原因。两台设备同时操作同一订单时，只允许一次有效推进，另一台刷新到真实状态。

正常流程不提供任意拖拽状态或批量完成按钮，避免店员误操作。需要特殊纠正时，通过订单异常处理入口记录处理原因，不用重复发送取餐通知掩盖问题。

### 4.3 新单与连接反馈

新付款订单进入时，在待接单区域显示明确提示和数量变化。提供一次主动开启声音的操作，声音受浏览器和设备限制，页面视觉提示始终有效。

接单等待过久时持续突出提示，具体阈值与无人接单处理方式待确认。首版方案不擅自改成超时自动接单，也不在未约定时限时自动取消已付款订单。

连接异常时持续显示“连接中断，订单可能未更新”和最后成功更新时间；恢复后重新获取未完成订单。首版可以采用短间隔自动刷新并保留手动刷新，不强制引入 WebSocket、独立叫号屏或打印设备。

刷新时保持店员当前阅读位置和已展开内容，避免整页闪动。恢复连接或普通刷新不把全部存量订单重新当作新单反复鸣响。

## 5. 门店与菜单操作

复用已有门店、分类、饮品和规格维护能力，咖啡界面优先突出：

- 饮品/规格售罄与恢复供应；不可售状态持续到手动恢复，首版不自动跨日重置。
- 商品上下架、价格修改、图片和规格编辑。
- 门店公告、营业状态及暂停接单。

饮品列表使用图片、名称、价格和可售状态，提供售罄快捷操作；复杂编辑放到详情表单。

“暂停接单”禁止新建订单，已支付订单仍需人工处理：待接单订单逐单确认接单或拒单退款，已接单订单继续履约。暂停前已创建的有效待支付订单若完成付款，也必须进入待接单并明确处理；不能因暂停营业静默丢弃。暂停确认中说明这一规则。

改价、售罄和下架不修改已创建订单的名称、规格和金额快照。新订单创建时由后端校验当前价格和可售状态；小程序的具体交互另行设计，不在本稿增加页面要求。

## 6. 订单、退款与流水

### 6.1 订单查询

支持按日期、取餐号、订单号和状态查询。默认今天，也能找到此前未完成或退款中的订单。

详情包含购买内容快照、订单金额、支付状态、制作/取餐状态、关键操作时间与操作者。取餐号按门店与日期区分，跨日查单同时显示日期，避免重复号码造成混淆。

制作状态、支付状态和退款状态分开表达。例如“制作中”不等于“已收款到账”，“退款申请已提交”不等于“退款成功”。

### 6.2 异常处理建议

- 未支付订单：在管理端订单查询中明确标记，不进入接单和制作队列；超时关闭规则在交易实施方案中约定。
- 已支付订单：咖啡管理员在订单详情处理取消/退款，避免退款和开始制作发生冲突；本稿不定义小程序申请退款的页面或入口。
- 待接单订单被店员拒绝：按拒单原因登记并发起整单全额退款，不以简单删除或隐藏订单代替退款。
- 无法制作：管理员在订单详情发起退款，填写原因；从制作任务中明确移出，保留可查询记录。
- 首版只做整单全额退款，不做部分退款、部分退杯、换购补差价。
- 退款中、退款失败需可见并可查询，最终结果以支付渠道确认的状态为准。处理中不允许重复发起同一笔退款。
- 已取餐后的售后仍可由有权限的咖啡管理员处理并留痕，不把它混进制作队列。

### 6.3 流水口径

订单与流水页顶部先提供四项：当日支付成功订单数、当日收款金额、当日退款成功金额、当日净收款。

收款按支付成功时间，退款按退款成功时间归属日期，均使用北京时间。净收款=当日收款−当日成功退款，因此历史订单今天退款也会影响今天的净收款。制作完成量另作为经营数据，不与支付订单数混用。

页面标注这是订单收退款统计，不是银行卡结算到账或扣除手续费后的利润。咖啡商户流水与原商品商户流水分别统计。首版不做复杂成本、利润、员工绩效和跨平台结算报表。

## 7. 工作台与提醒服务的衔接

此前已提出微信制作完成提醒的需求。本稿只约定管理端与提醒服务的衔接：店员点击制作完成后，先可靠保存待取餐状态，再产生通知任务；通知失败不回退制作状态，也不把订单自动标为已取餐。

相同制作完成事件不产生多条独立通知任务；发送结果在后台可追踪。模板与用户授权是提醒服务实际发送的前提，具体微信接入与小程序交互另行编写方案。本稿不新增顾客页面、联系门店入口、适老化界面或独立客户端。

店员按取餐号核对当前订单后确认取走，保留操作记录。

## 8. 首页广告与推荐养护：最小改造方案

### 8.1 展示位置与布局

在现有首页“顺时养护”下面展示运营内容，保留当前绿色背景、节气视觉、双业务入口和整体字体风格。

从上到下安排：一张当季主推图，以及可选的“推荐养护”产品区域。主推图和推荐养护可分别配置；没有有效内容时，对应区域自然收起，不补空白框。

主推图复用现有 `home_banner`，从有效记录中取排序最高的一条。其他已有记录保留在后台，不因首页改成单图而删除。

推荐养护每行两个产品，最多三行。配置一个、三个、五个时，末行保持正常宽度靠左排列；不凑数、不放大单个项目，也不增加“查看更多”或新列表页。未配置推荐时不显示标题及网格。

每个推荐展示图片、名称、一句简短推荐理由。统一图片比例和文字排版，保留留白，不再给整个推荐区套明显的边框和外层卡片。

### 8.2 数量与排序

后台可以自行增加多条推荐记录，前台最多展示六条有效推荐，不固定为两个。两个只是可采用的初始内容数量。

“有效”沿用现有启用状态及起止时间规则。按现有排序值从高到低排列，同值沿用现有 ID 降序规则；超过六条时只展示前六条，其余保留供后续调整。首版不额外增加商品自动去重规则，运营配置时避免重复推荐同一产品。

后台位置名称注明“首页推荐养护（最多展示6项）”，并提示超出数量时按排序取前六条。起止时间沿用现有服务处理，不增加定时任务系统。

### 8.3 运营如何配置

复用当前“活动运营”列表及表单，新增位置值 `home_recommend`。运营选择位置后，填写标题、图片、副标题作为推荐理由，配置跳转、状态、排序和投放起止时间。

商品沿用 `product` 跳转类型及商品 ID。咖啡若作为运营内容，首版可沿用 `page` 跳转到已有咖啡菜单；不声称已有饮品定位或直接选规格能力。具体页面路径在实施时使用项目实际路由。

为控制工作量，暂不新增商品搜索选择器，继续使用现有商品 ID/页面路径输入方式；不展示人工录入的价格，实际售价在业务详情或菜单中查看。

首页展示只使用运营配置的图片与文案。本轮最小方案不承诺商品下架后自动移除推荐，也不自动联动咖啡售罄状态；运营需同步停用失效内容，跳转后的商品详情或咖啡菜单沿用实际可售校验。若要求自动联动，应单独评估关联业务数据查询的改动。

### 8.4 改动范围与暂缓能力

| 部分 | 最小改动 |
| --- | --- |
| `c-uniapp/src/pages/home/index.vue` | 主推改为单张展示；读取推荐位置内容，最多六条并按双列布局展示；复用现有跳转逻辑 |
| `admin-web/src/utils/format.js` | 增加推荐养护位置选项、名称和六项展示限制说明 |
| 现有广告业务接口及数据库 | 复用 `marketing_activity` 与现有查询/维护能力；纯展示需求无需新增 Java 业务接口或改表 |

六项限制说明如果现有表单无法从选项文案清楚表达，可在现有运营页补一行说明，仍属于小型前端改动。最终文件清单以实施检查为准，不把“两个文件”作为不能调整的硬约束。

后台 RBAC 是另一项必需改造：现有运营管理接口同样需要服务端权限保护。“广告展示无需新增后端接口”不等于本轮分权可以跳过这些接口。

不纳入本轮：草稿与发布审批、投放冲突提醒、后台预览、曝光/点击统计、实时价格、智能推荐、自动下架联动、自由排版专题页及复杂轮播策略。现有公告和弹窗配置保留兼容，不因本轮展示调整删除原数据或语义。

首次增加首页布局需要发布小程序版本；之后在这些既定位置更换文案、图片、排序、时间和跳转目标，可由后台完成。新增页面或交互仍需发版。

### 8.5 运营权限与消息边界

超管可维护共享首页广告及推荐养护。是否同时授权商品管理员维护共享首页，是尚待确认的权限选项；不默认给咖啡管理员共享首页的编辑发布权，也不为此增加跨店审批流程。

这里的运营内容是用户打开首页时读取并展示的页面内容，不调用微信订阅消息主动发送广告。咖啡制作完成提醒继续按第 7 节单独规划。

先实施分权基础和超管账号管理，再打通咖啡订单支付与退款，随后联调制作工作台与提醒服务。首页运营展示可独立实施，并与最终运营权限共同验收。小程序的交易接入改动另在前端实施方案中定义，不在本稿扩展。工作台可以先用开发数据验证布局，但这不能作为真实交易验收。

## 10. 验收应看到的结果

1. 超管能创建账号、分配角色与咖啡门店、启停用和重置密码；非超管不能操作这些接口，不能移除最后一个启用超管。
2. 三类账号进入正确界面，越权访问页面及直接请求接口均无法取得另一业务的数据；停用、改角色或门店授权、重置密码后的会话按新规则受控。
3. 咖啡支付确认后，订单只进入一次待接单，人工确认后才能进入待制作；使用咖啡商户收款，不触发商品库存和分销流程。
4. 两个店员同时接单、拒单或推进制作不会产生冲突的有效结果；拒单后退款可追踪；卡片规格完整，工作台与服务端订单状态一致。
5. 制作完成后显示待取餐；没有授权或通知发送失败不回退制作状态，不妨碍管理员确认取走。
6. 暂停接单和售罄不丢失已支付任务，断网/重连不呈现虚假的正常空队列。
7. 全额退款可追踪最终结果，重复请求不重复退款，流水口径能用实际支付与退款记录核对。
8. 原商品登录、商品后台、下单、支付和历史数据继续正常使用。
9. 首页主推只展示一条；推荐配置 0、1、2、3、5、6 及超过 6 条有效记录时，数量与单双数排版正确，最多展示六条，后台其余记录保留。
10. 广告启停用、有效期和排序沿用现有规则；商品及已有页面跳转正常，未配置内容自然收起，运营区域失败不影响商品与咖啡业务入口。
11. 原公告、弹窗配置和广告数据保留；后台运营接口执行与最终确认角色一致的权限检查。

## 11. 已确认规则与待讨论项

用户已确认：

- 首家门店位于医院，下单老年顾客较多；首版必须人工接单，并规划接单接口。
- 一单多杯整体制作完成、整体取走，不拆杯流转。
- 咖啡管理员处理退款，首版整单全额退款。

- 首页广告采用此前讨论的最小改造；推荐养护可自行增加产品，前台最多六个，不固定为两个。
